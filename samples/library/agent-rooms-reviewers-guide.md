# Reviewers

## 0. Audit history

Two external audits were performed on July 24, 2026, against the state of this repository at that time. Both audits found defects across all five of the load-bearing claims in section 3 below: the adoption path, server-side identity, model routing, token-budget enforcement, and provenance-chain integrity. Every finding from both audits was fixed in three commits landed the same day: 89c6a28 (auth: GitHub sign-in, server-derived identity, removal of client-supplied actor ids), f29efe7 (truthful adoption and provenance: fail-closed merges, row locks, repo path policy, a real secret scan), and 9983627 (budget enforcement and routing attestation: atomic reservations, a kill switch, provider verification).

A third round of external review followed, on the post-hardening code, and found fourteen further defects. All fourteen were fixed in one commit, "Re-audit fixes: immutable identity, durable adoption, path normalization, authenticated reads": identity re-keyed onto GitHub's immutable numeric account id, adoption restructured so the merge runs outside any transaction with a crash-safe recoverable attempt record, an explicit pending/published state on proposal versions, baseSha added to the fork bundle, the apply step's own baseSha made authoritative, exactly-once budget settlement with stale-reservation recovery, a hard max_tokens output bound, fail-closed provider attestation that aborts the stream, a normalized path deny-list, promote branch rollback covering mid-apply failures, authenticated reads on the room/messages/proposal endpoints and the room page, a maintainer-management route and CLI, and database-level immutability for published proposal versions with explicit broken-link reporting in lineage. Sections 2 through 5 below describe the state after that commit.

This document has been rewritten from scratch against the code as it exists after those three commits, then updated for the fourteen re-audit fixes. It describes the post-fix state, not the state either audit examined. Reviewers should treat this as a new baseline and re-audit the current code rather than assume any specific finding from the earlier audits still applies, since the mechanism it applied to may no longer exist in the form it was found in.

## 1. What this is

Agent Rooms is a product built around rooms where builders chat together, and each builder also has a private AI agent sidebar that only they can see. Promote takes a piece of that private agent's output and publishes it as a Proposal, which opens a real GitHub pull request against the room's linked repository. Adopt is a maintainer merging that pull request with the head commit SHA pinned to what was actually promoted, so the merged code carries a verifiable credit and lineage trail back to its author and its forks.

For the full data model and the invariants that the schema and routes are built to preserve, read docs/design/promote-provenance.md. For the history behind why v0 looks like it does, read the three ADRs in docs/decisions/: 0001-promote-provenance-first.md argues for building the provenance data model before any UI existed, 0002-attach-dont-build.md is the pivot to attaching to Discord and GitHub instead of building a standalone platform with a custom ledger, and 0003-polished-core-narrow-breadth.md is the second pivot to a polished single-room web product with a hosted agent sidebar, narrowed to one repo type and one adoption method, because the actual test population is vibe-coders rather than CLI-native developers. All three paths were confirmed to exist and were read in full for this document.

## 3. The five load-bearing claims and where they live

**SHA-pinned, fail-closed adoption.** The route is app/src/app/api/adopt/route.ts. It requires a real server-derived session (401 if `getCurrentContributorId` returns null) and requires that contributor be in `room.maintainers` (403 otherwise). owner/repo/pullNumber/expectedHeadCommit are never taken from the request body: they come from the room's `githubRepoRef` and from the exact `proposalVersionId` the caller asked for, looked up directly from the database and pinned (never silently substituted for the latest version; a stale or wrong `proposalVersionId` gets a 409 if it is not the latest published version, or a 404 if it does not exist at all). Three fail-closed exits precede any GitHub call: a version with no `prNumber` returns 409 with nothing recorded; `credsPresent()` returning false (GITHUB_APP credentials absent) returns 503, because the route refuses to claim a truthful adoption happened when it cannot ask GitHub to verify one; and a state-machine check via `canTransition` in app/src/lib/stateMachine.ts returns 409 if the proposal is not `open`. The merge never runs inside a transaction and never holds a row lock across the HTTP round trip to GitHub. It runs in three phases. A first transaction `SELECT ... FOR UPDATE`-locks the proposal row, re-checks the state transition and the exact version pinning against the locked row, and records a *pending* Adoption attempt, then commits. The merge then runs with no locks and no open transaction, calling `mergePullRequest` in app/src/lib/github.ts with the stored `headCommit` as `expectedHeadCommit`; that function passes it through as the `sha` parameter to GitHub's pull-request merge endpoint, so GitHub itself rejects the merge if the PR head has moved since promotion. A rejected merge deletes the pending attempt and surfaces as a 409 with nothing recorded. Only on a real merge does a second transaction lock the proposal again, finalize the Adoption row with the real merge SHA, and transition the proposal to `adopted`. This is what makes the path crash-safe: a process that dies between the merge and the finalize leaves a pending attempt behind, and the next adopt request for that proposal does not merge again. It reads the PR's state from GitHub and either finalizes the existing attempt (the merge already happened) or releases it (the merge never happened) so a clean retry is possible. Recovery only applies to an attempt older than `ADOPTION_ATTEMPT_RECOVERY_MS`; a younger pending attempt belongs to a request in flight right now and a concurrent caller gets a 409 rather than stealing it. As a second, database-enforced line of defense against a duplicate Adoption row (a race between two concurrent adopt requests, or a retried request), `adoptions.proposalId` carries a UNIQUE index (migration 0005, `adoptions_proposal_id_idx`), so at most one Adoption row can ever exist for a given proposal even if the application-level check were somehow bypassed.

**Server-derived identity and the privacy boundary it protects.** Identity is resolved server-side, never trusted from the client. app/src/auth.ts configures Auth.js (NextAuth v5) with a GitHub OAuth provider (`clientId` defaults to the registered app id if `GITHUB_OAUTH_CLIENT_ID` is unset; `clientSecret` has no default and is required for a real sign-in to complete). Its `jwt` callback calls `findOrCreateContributorByGithub` in app/src/lib/contributor.ts on the sign-in profile, which finds-or-creates a Contributor row keyed on `linkedGithubUserId`, GitHub's immutable numeric account id, backed by the unique index in migration 0007, and stashes that Contributor id on the token. The GitHub *login* is deliberately not the key: a login is renameable and a released login can be claimed by a different account, so keying on it let a renamed-then-reclaimed username inherit the original contributor's private agent sessions and maintainer authority. The login is now display metadata only, refreshed at every sign-in and released from whichever contributor previously held it. Seeded demo contributors have a NULL `linkedGithubUserId`, and a NULL never equals anything in SQL, so no real GitHub account can ever resolve to a seeded persona. A profile with no numeric id is refused outright rather than falling back to the login. The `session` callback copies it to `session.contributorId` (typed via app/src/types/next-auth.d.ts). Every mutating route calls `getCurrentContributorId` in app/src/lib/session.ts, which calls Auth.js's own `auth()` and returns `session.contributorId` or `null`; callers treat `null` as unauthenticated and respond 401 before doing anything else. Reads are gated the same way now: `GET /api/rooms/[id]`, `GET /api/rooms/[id]/messages`, and `GET /api/proposals/[id]` each 401 an anonymous caller rather than returning the room, the chat stream, or the full diff and remix note, and the room page itself redirects an anonymous visitor to sign in instead of rendering the whole room. A development-only fallback exists: only when `NODE_ENV === 'development'` AND `DEV_IDENTITY_FALLBACK === '1'` are both true does the function instead return the seeded `DEV_FALLBACK_CONTRIBUTOR_ID` (`'contributor_priya'`), so local demo/verify scripts keep working without a real GitHub sign-in; this is off by default and the `NODE_ENV` check means it cannot resolve in a production build regardless of the flag. This is also what makes the still-true privacy-boundary claim actually mean something: the private agent lives behind app/src/app/api/agent/message/route.ts, which reads and writes only the `agent_sessions`/`agent_messages` rows keyed uniquely by `(ownerContributorId, roomId)`, and the system prompt built in `buildSystemPrompt` in that same file tells the model "You discuss, plan, and draft privately with this one builder. You never see other builders' private chats." Before this identity work, every actor in the app was the same hardcoded contributor id, so a "private per builder" boundary had no distinguishable builders to actually keep apart; now that identity is real, the boundary is enforced between genuinely different contributors. Reinforcing this, every client-supplied actor-id field (`authorContributorId`, `byContributorId`, `adoptedByContributorId`, `rejectedByContributorId`) was removed from every zod schema in app/src/lib/validation.ts, and every schema there is `.strict()`, so a client that still sends one of those fields gets a 400 instead of it being silently ignored or, worse, trusted as an impersonation vector.

**US/EU-pinned model routing with provider attestation.** app/src/lib/model.ts defines `export const PINNED_US_EU_PROVIDER_SLUGS = ['openai'] as const;` and sets `body.provider = { only: [...PINNED_US_EU_PROVIDER_SLUGS], allow_fallbacks: false, data_collection: 'deny' }` on every OpenRouter request. The model switched from DeepSeek V4-Flash to GPT-5.6 Luna on 2026-07-30; the pin, originally built to keep an open-weight Chinese model off China-hosted resellers, is retained as a first-party-only pin so a future model swap cannot silently reopen the routing question. New in this pass: the production OpenRouter base URL is now the hardcoded constant `PRODUCTION_OPENROUTER_BASE_URL`, and `resolveBaseUrl()` only ever honors the `MODEL_BASE_URL` env override when `process.env.NODE_ENV !== 'production'`; in a production build the override is never read at all, closing an escape hatch that previously would have let anyone who could set an env var (a misconfigured deploy, a compromised CI job) redirect every inference call, bearer key included, to an arbitrary host. Also new: `streamChatCompletion` now parses the top-level `provider` field OpenRouter sends on every streamed chunk (verified live on 2026-07-24 against a real streamed response) and returns it as `StreamResult.provider`. `isAllowedProvider()` checks that value against the pinned slugs case-insensitively and fails closed on a missing provider: "we cannot confirm where this was served" carries the same risk as a confirmed off-policy provider, and treating absence as allowed meant an endpoint that simply omits the field bypassed the pin entirely. The check is a gate rather than a log line. The first streamed chunk carrying a provider decides whether the request continues at all: on a missing or off-policy provider `streamChatCompletion` cancels the reader, throws `OffPolicyProviderError`, and logs `console.error('[SECURITY] off-policy model provider served a request...')`. The agent route then persists no assistant message, releases the budget reservation, and returns an error event carrying `code: 'off_policy_provider'`, so an off-policy endpoint never streams a whole response into a private session and never has that response stored. The gate is skipped only when the non-production `MODEL_BASE_URL` override is active, since a local mock server does no provider routing and can attest nothing; that override is itself already hard-gated to non-production. `servedProvider` and `offPolicy` remain on `agent_messages` (migration 0006) for rows recorded before this gate existed.

**Server-side, atomic token-budget enforcement.** app/src/lib/budget.ts replaces a prior sum-then-write check (vulnerable to a TOCTOU race where two concurrent requests could both pass the same cap) with `reserveUsage`, which runs entirely inside one `db.transaction`: it `SELECT ... FOR UPDATE`-locks the room row (serializing concurrent requests to that room so a second request cannot race past a cap check the first request has not yet committed), checks `rooms.killSwitchEnabled` (423 if a maintainer has disabled the agent for the room), validates `AGENT_DAILY_TOKEN_CAP` and the room's `tokenBudgetPerRoom`/`tokenBudgetPerUser` (a non-numeric or negative env value fails closed to the documented default cap rather than silently disabling the check; a negative room-level cap, which can only reach the database by bypassing the API's positive-int zod validation, fails closed to 0 rather than "no cap"), and only if every check passes, inserts an `agent_usage_reservations` row and increments `rooms.tokenBudgetUsed`, all before the model is ever called in app/src/app/api/agent/message/route.ts's POST handler. `reconcileUsage` settles the reservation to the real token count once the stream completes; `releaseReservation` backs the estimate back out if the model call fails, is refused off-policy, or the client aborts the stream. Both go through one settle path that locks the *reservation* row `FOR UPDATE` and requires it to still be `pending`, so settlement is exactly-once: a retried reconcile, a double release, or a release arriving after a commit finds a non-pending row and is a no-op, and a late release can never erase already-recorded usage. `reserveUsage` also sweeps stale reservations on the admission path: anything still pending after `PENDING_RESERVATION_TIMEOUT_MS` is treated as abandoned by a crashed request and released, so ghost estimates cannot permanently consume a room's caps. The estimate itself is now a genuine upper bound, character-based (`ceil(chars / 3)` plus a documented per-message framing overhead) rather than a whitespace word count that a dense, unspaced payload could game down to a couple of tokens, and its output half is sent to the model as `max_tokens`, so actual usage cannot exceed what was reserved. The four distinct refusal outcomes are `kind: 'kill_switch'` (423), and `'daily_cap'` / `'room_cap'` / `'user_cap'` (each 429), so a caller can tell which specific budget was exhausted.

**Provenance chain integrity.** The chain is still the `proposals`, `proposal_versions`, `forks`, and `adoptions` tables in app/src/db/schema.ts: `proposals` carries `parentProposalIds` for cross-room DAG lineage, `proposal_versions` carries an explicit `status` of `pending` or `published` and is immutable once published, enforced at the database level by the `proposal_versions_freeze` trigger in migration 0007, which rejects any UPDATE of a frozen column and any DELETE of a published row. The single permitted mutation is the pending-to-published finalization in the promote route, which fills in the real `baseSha`/`headCommit`/`contentHash`/`prNumber`/`prUrl` once the branch and PR actually exist. Promote inserts the row pending, so nothing can fork, adopt, or display an in-flight promote whose PR does not exist yet and whose hashes are still placeholders; the trigger recognizes one explicit, session-scoped escape (`agent_rooms.allow_provenance_mutation`) used only by test fixtures and the demo seed script to tear down rows they created, and set by no application code. `proposal_versions` and stores the exact `headCommit` and `prNumber` a fork or adoption consumed, `forks` records who forked which exact `proposalVersionId`, and `adoptions` records `adoptedByContributorId`, `expectedHeadCommit`, and the resulting `mergeCommitSha`. New in this pass: `adoptions.proposalId` carries a UNIQUE index (migration 0005) so a proposal can be adopted at most once at the database level, not only by application logic. `app/src/lib/lineage.ts` gained `validateParents`, called from app/src/app/api/proposals/route.ts before a new Proposal is inserted: every `parentProposalIds` entry must already exist (400 with the missing ids otherwise) and none may create a cycle in the Proposal DAG (400 otherwise), walked with the same visited-set traversal `buildLineageChain` uses to assemble the ancestry shown on a proposal page. `app/src/lib/hash.ts`'s `computeContentHash` now length-prefixes each field (`` `${field.length}:${field}` ``) before concatenation instead of joining with a plain separator, closing a field-boundary collision where two different splits of adjacent fields (for example between `baseRef` and `baseSha`) could produce the same canonical string. `app/src/lib/github.ts`'s `createBranchAndApplyDiff` now calls `findForbiddenPaths` against the named `FORBIDDEN_DIFF_PATH_RULES` before creating any blob, rejecting (as a `PathPolicyError`, surfaced by the promote route as a 400 with the rejected paths) any file under `.github/` or `.git/`, any path containing `..`, any absolute path or path containing a backslash, `package.json`/`package-lock.json` anywhere in the tree by basename, or a root-level dotfile. Every rule runs against a normalized path (app/src/lib/repoPath.ts, also applied by both diff parsers), with directory prefixes compared case-insensitively, so `./.github/workflows/pwn.yml`, `.GitHub/workflows/x.yml`, `./.env`, `./package.json`, and `packages/app/package.json` are all rejected; each of those walked straight through the previous raw `startsWith` and exact-equality rules. `buildLineageChain` in app/src/lib/lineage.ts no longer silently drops an ancestor id with no row behind it: it returns the id as an explicit broken-link node, and the proposal page renders a visible "Broken lineage" warning naming the missing ancestors, so an incomplete chain cannot read as complete provenance. `proposal_versions.baseRef` and `baseSha` are now two separate columns (migration 0005 renamed the previously mis-named `base_commit` column to `base_ref` and added `base_sha`), so the human-readable ref and the resolved commit SHA are distinct, independently verifiable facts instead of one field standing in for both.

## 4. How to run and verify

The app reads these environment variables (see app/.env.example for the canonical, commented list): `DATABASE_URL`, `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_INSTALLATION_ID`, `OPENROUTER_API_KEY`, `AGENT_DAILY_TOKEN_CAP`, `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET`, `AUTH_SECRET`, and optionally `MODEL_BASE_URL` and `VERIFY_BASE_URL`. Copy app/.env.example to app/.env and fill these in. `DATABASE_URL` is required for essentially everything, since the database connection in app/src/db/client.ts is only deferred, not optional. `GITHUB_OAUTH_CLIENT_ID` defaults to the registered app's id if left unset, but `GITHUB_OAUTH_CLIENT_SECRET` has no default; without it, GitHub sign-in cannot complete (Auth.js shows its own error page rather than the app failing to boot). `AUTH_SECRET` signs Auth.js sessions; when the GitHub or OpenRouter variables are absent, the adopt route and the model client fall back to fail-closed or stubbed behavior rather than silently succeeding, as described in section 3.

One variable needs an explicit warning: **`DEV_IDENTITY_FALLBACK` must never be set to `1` in a production environment.** When it is `1` and `NODE_ENV=development`, app/src/lib/session.ts resolves every unauthenticated request to the seeded `contributor_priya` identity so local demo and verify scripts work without real GitHub sign-in. The code gates this strictly behind `NODE_ENV === 'development'` as well, and separately refuses it on any hosted deployment by reading the platform's own `VERCEL` and `VERCEL_ENV` variables, so it cannot activate in a real production build regardless of this flag. The flag itself should still never be present in a production `.env` or deploy configuration, since its absence is what makes the check safe to reason about at a glance.

Standard commands, run from the app directory: `npm run dev` starts the Next.js dev server, `npm run build` produces a production build, `npm run test` runs the Vitest suite, `npm run db:generate`/`npm run db:migrate` manage Drizzle migrations, `npm run seed` idempotently loads the legacy hand-written Night Market fixture, and `npm run demo:curate` builds the actual seeded demonstration room out of real Stage 0 chains (`-- --http-only --live-fork` and `-- --http-only --reject` are its two opt-in steps that talk to the running app, the second of which closes a real pull request). `npm run room:repo` bootstraps a canonical room repo via `create-room-repo.ts`, and `npm run room:maintainers -- <contributorId> [roomId]` bootstraps a room's maintainer roster. The three browser-driven verify scripts (`npm run verify:chat`, `npm run verify:ui`, `npm run verify:agent`) each set `DEV_IDENTITY_FALLBACK=1` inline in their package.json script definition and require the dev server already running on http://localhost:3000 (or `VERIFY_BASE_URL`); `verify:agent` can be pointed at a local mock model server via `MODEL_BASE_URL` if the OpenRouter account has no credits.

The Vitest suite (`npm run test`) currently comprises 22 test files and 207 tests, all passing as of this writing, run against the real local Postgres from `DATABASE_URL` (loaded via `vitest.setup.ts`'s `dotenv/config`). It covers: `diff`, `unifiedDiff` (fenced-unified-diff-to-structured-files conversion), `forkBundle`, `hash` (including the length-prefix collision case), `remixNote`, `stateMachine`, `secretScan` (the expanded pattern table), `contributor` (find-or-create by immutable GitHub account id, including rename, login-reclaim, and seeded-persona cases), `validation` (the actor-id-stripped, `.strict()` schemas), `lineage.parents` (parent-existence and cycle validation), `budget` (atomic reservation, kill switch, all three cap kinds, and the UTC-day windowing of each), `model` (fail-closed provider attestation, stream abort, `max_tokens`, and the production-only base-URL gate), `github` (the normalized repo-write path-policy deny-list, every bypass variant included), and `provenance` (the database-level immutability trigger and lineage broken-link reporting). Eight suites are route-level integration tests that exercise real Postgres transactions end to end rather than re-implementing the DB behavior as a fake: `adopt.route.test.ts` (including crash-safe attempt recovery with no second merge), `promote.route.test.ts` (the proposals route, including branch rollback after a mid-apply failure and the authoritative baseSha), `fork.route.test.ts`, `maintainers.route.test.ts`, `killSwitch.route.test.ts` (including an integration case that flips the switch and then asserts `reserveUsage` actually refuses), `readGates.route.test.ts`, `rooms.route.test.ts`, and `agentMessage.route.test.ts`; these mock only `'octokit'` and `'@/lib/session'`, using shared fixtures in app/src/lib/__tests__/testDb.ts (`makeContributor`, `makeRoom`, `makeProposal`, `makeVersion`, `makeFork`, `makeAgentSession`, and a `cleanup` helper) to set up and tear down real rows per test.

The three verify scripts also connect to the live local database and both insert and delete rows as part of their run, matching against the exact strings they just posted. Do not run them against a database you care about, and do not run them concurrently with someone else using the same seeded room, since a verify script's cleanup step could delete rows it did not create if content happens to collide.

## 5. Known gaps

**GitHub OAuth sign-in is confirmed working locally,** which closes what this section previously listed as a gap. An earlier version of this document reported `GITHUB_OAUTH_CLIENT_SECRET` as empty and sign-in as never exercised; both statements are now out of date. The secret is populated, and a real sign-in has been completed through the GitHub flow against the local dev server, creating a Contributor row keyed on the operator's immutable numeric GitHub account id with the login stored as display metadata only, verified in the database rather than inferred from the UI. The credential is the registered GitHub App's own OAuth, not a separate OAuth App: the client id carries GitHub's `Iv23` App prefix and app/src/auth.ts hardcodes that same id as its fallback, so the callback URL lives in the GitHub App's settings alongside its `contents:write` / `metadata:read` / `pull_requests:write` permissions. Only `http://localhost:3000/api/auth/callback/github` is registered today. What remains unverified is narrower and worth stating: sign-in has been exercised against localhost only, by one account, and never against a deployed origin, where Auth.js's host-trust behavior and the callback registration both differ. Auth.js v5 sets `trustHost` automatically when `VERCEL` is present (`@auth/core/lib/utils/env.js`), so no code change is needed for that, but it has not yet been observed working.

**The development identity fallback is a real, live code path, now behind two independent gates.** app/src/lib/session.ts's `DEV_FALLBACK_CONTRIBUTOR_ID` mechanism is not dead code: it is what every local `npm run dev` session and all three verify scripts currently authenticate as, since `DEV_IDENTITY_FALLBACK=1` is set in this environment's `.env` and is set inline by the verify:* npm scripts themselves. Its safety used to rest entirely on `NODE_ENV` being correctly set to `'production'` by the deploying platform. It now also requires `onHostedDeployment()` to be false: that function returns true when `VERCEL_ENV` is `production` or `preview`, or when `VERCEL=1` without `VERCEL_ENV=development`, so a deployment would need both `NODE_ENV` and the platform's own system variables to be wrong before an unauthenticated request could resolve to the seeded identity. The Stage 0 header override sits behind the same gate. app/src/lib/__tests__/session.test.ts covers both. What remains true: the second gate is specific to Vercel, so a deployment on another platform is back to relying on `NODE_ENV` alone until an equivalent check is added for it.

**Maintainer rosters can be changed after room creation** through `POST /api/rooms/[id]/maintainers` (maintainer-only, room row locked, last maintainer cannot be removed) and the `npm run room:maintainers` CLI for bootstrapping a roster nobody is yet authorized to edit. **The kill switch now has a maintainer-facing control too**, closing what was previously listed here as a gap: `POST /api/rooms/[id]/kill-switch` is maintainer-only, resolves the actor from the session, locks the room row for the read-check-write, and takes the desired state as a boolean rather than a toggle so a double-submitted emergency stop is a successful no-op instead of a flip back on. A body naming a different room than the path is refused with a 400 rather than one silently winning. `rooms.killSwitchEnabled` remains enforced in app/src/lib/budget.ts's `reserveUsage`, which returns `kind: 'kill_switch'` and a 423 on every agent message for a room with it set. There is still no UI affordance for it; it is an API-and-CLI control, not a button.

**All three token budgets are now windowed on one boundary,** closing what was previously listed here as a gap. Previously only the global `AGENT_DAILY_TOKEN_CAP` reset: the room cap compared `tokenBudgetPerRoom` against `rooms.tokenBudgetUsed`, a monotonic counter that was never reset, and the user cap summed `agentUsageReservations` with no date filter at all, so both were cumulative forever and a room that exhausted its budget stayed exhausted until an operator edited the column by hand. This was not hypothetical; it ended a Stage 0 run mid-flight. In app/src/lib/budget.ts's `reserveUsage`, all three checks now filter reservation rows by `gte(agentUsageReservations.createdAt, windowStart)` where `windowStart` is a single `startOfDayUtc()` value computed once before the transaction opens, so a request straddling midnight cannot have the three caps disagree about which day it is in, and all three reset together at 00:00 UTC. The room cap is derived from that room's reservation ledger rather than from `rooms.tokenBudgetUsed`, because a counter with no timestamps in it cannot be windowed at all. Only `pending` and `committed` rows count toward any cap, so a `released` reservation from a failed, off-policy, or aborted request counts toward none. `rooms.tokenBudgetUsed` is still maintained on reserve, settle, and stale-sweep, but it is now a lifetime figure for display and debugging and is no longer an input to any admission decision. What remains open is narrower: the window is a fixed UTC day rather than a rolling window or a per-room configurable period, and there is still no way to raise a cap or forgive usage from the API, so an operator who wants either must update the row directly.

**Live updates are still a poll, not a push.** app/src/components/LiveRefresh.tsx still calls `router.refresh()` every three seconds on a fixed interval so that messages or proposals posted by someone else appear without a manual reload; there is no websocket or server-sent-event channel. Unchanged by the three hardening commits.

**Repo creation still shells out to the gh CLI.** app/src/lib/github.ts's `createRoomRepo` still calls the `gh` CLI using the operator's own authenticated shell session, because the installed GitHub App has `contents:write`, `metadata:read`, and `pull_requests:write` only, and GitHub Apps cannot create repositories on a user account without an `Administration:write` permission this app does not have (verified live: `POST /user/repos` returns 403). Every other GitHub operation (seeding, branching, diff application with the new path policy, opening PRs, and the SHA-pinned merge) goes through the GitHub App. Unchanged by the three hardening commits.

**Write routes are rate limited per contributor; nothing limits anonymous or read traffic in app code.** app/src/lib/rateLimit.ts gives each signed-in contributor a ceiling per action: 10 rooms an hour, 30 chat messages a minute, 20 promotes per ten minutes, 60 forks per ten minutes, and 60 adopt or reject decisions per ten minutes. The room-creation, chat-message, promote, fork, adopt, and reject routes call it immediately after the 401 check and before the body is parsed, so malformed requests count too, and answer 429 with a `Retry-After` header. Each check runs in one transaction under a `pg_advisory_xact_lock` keyed on contributor and action, counts that contributor's rows in `rate_limit_events` (migration 0010) inside the window, and writes a row only when there is room, so a burst of simultaneous requests admits exactly the ceiling. What it does not do: the key is the contributor id, so it says nothing about unauthenticated requests, which every limited route already refuses with 401 before touching the limiter; rate limiting those is left to the hosting platform's firewall. The read routes, the maintainers route and the kill-switch route are not limited. One deliberate fail-open: if `rate_limit_events` does not exist, because a deploy ran ahead of its hand-applied migration, the limiter logs a `[SECURITY]` line and allows the request instead of turning every write route into a 500; any other database error still throws. Who can sign in at all is bounded separately by `AGENT_ROOMS_ALLOWLIST` (app/src/lib/allowlist.ts), re-checked on every session read, and that bound holds only while the variable is set on the deployment.

**Q&A answered-by/asked-by matching is still unconstrained free text.** app/src/db/schema.ts still stores `qa_exchanges.askedBy` and `answeredBy` as plain text columns with no foreign-key reference to `contributors`, and app/src/app/proposal/[id]/page.tsx's `nameFor` helper looks values up against a map keyed by contributor id, falling back to the raw string if no match is found. In app/scripts/seed.ts these columns are always populated with contributor ids, so the display-name-matching failure mode does not currently reproduce; the real, narrower gap is that the columns are unconstrained rather than enforced foreign keys, so a future caller that passed a display name instead of an id would silently fail to resolve without any database-level error surfacing the mismatch. Unchanged by the three hardening commits.

**The demonstration room's provenance is real; its conversation is authored fiction.** app/scripts/curate-demo.ts builds the `night-market` room out of five chains the Stage 0 run actually produced, so every card's pull request number, base ref, head commit, content hash, and merge commit is the value that was really recorded, and the chains are re-parented rather than copied so no second row ever claims the same pull request. The room chat and the Q&A exchanges are written by that script and describe events the agents did not actually discuss, because Stage 0's personas never talked to each other. This is the seeded demonstration room ADR 0003 and the design doc call for, and it is labeled: the room is named "Night Market (demo)" and its first message, from a non-person contributor named "Agent Rooms", states that the builders are seeded personas and that the chat is narration over real events. A reviewer should read card provenance as verified and chat as staged. One further consequence of using real data: Stage 0 rejected nothing, so the single rejected card required rejecting a real leftover proposal through the real route, which closed its pull request on GitHub without merging.

**Stage 0's payload-sufficiency arm was removed as never valid.** The validation protocol originally gave Stage 0 a fourth purpose: cycling rich, thin, and absent remix notes to separate payload failures from disinterest before the jams conflated them. It could not produce a result, for two independent reasons. Every arm scored four of four, a ceiling effect from tasks small enough to complete from the diff alone; and the "rich" arm emitted the same canned bullets on every proposal, describing the harness's own constraints rather than the specific change, so it compared a thin note against a differently-worded thin note. The deeper problem is that a forking agent does not experience the comprehension cost a remix note exists to reduce, so no variation of the arm could measure it. The arm and its per-arm reporting are gone from app/scripts/stage0.ts, along with its `payload-too-thin` dead-fork cause, which attributed failures to a payload difference that did not exist. The validation protocol, which is kept out of this repository while the human test runs, records this and leaves the question to the human sessions. Any earlier Stage 0 numbers broken out per arm, including those in app/stage0-results.json, should be read as carrying no information about note quality.

**Stage 0 did not exercise real authentication.** app/scripts/stage0.ts identifies its five personas with an `x-stage0-contributor-id` header that app/src/lib/session.ts honors only when `NODE_ENV=development`, `DEV_IDENTITY_FALLBACK=1`, and `STAGE0_IDENTITY_OVERRIDE=1` are all set and the process is not a hosted deployment. Every route, validation path, and database transaction in the loop was therefore exercised as a signed-in user would exercise it, except the sign-in itself: nothing in that run proves a real GitHub OAuth sign-in resolves to the same contributor id, and app/src/auth.ts's callback wiring is not touched by the harness. This is the same gap as the first item in this section, seen from the Stage 0 side rather than the code side.

Recent commits, from `git log --oneline`, show the schema and core API landing first per ADR 0001, several rounds of UI and typography polish, then the GitHub round-trip and SHA-pinned adoption landing alongside the sidebar agent's US-pinned routing, and finally, on July 24 2026, the three hardening commits named in section 0 landing in sequence (auth, then adoption/provenance, then budgets/routing) in response to the two external audits. The gaps listed above are what remain open after that work, not regressions from a prior working state.
